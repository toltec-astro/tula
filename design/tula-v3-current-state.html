Responsibility split

Conan owns dependency orchestration; Tula owns feature policy

Conan 2

  • settings and profiles
  • recipe options and requirements
  • dependency graph
  • CMakeDeps
  • CMakeToolchain and presets

tula_cmake

  • feature/provider registry
  • selection validation
  • CPM and system providers
  • normalized tula::* targets
  • generated config header

Downstream CMake

  • calls resolver after project()
  • links logical targets only
  • does not select a provider
  • does not run Conan internally

Boundary: provider selection is fixed during conan install. CMake executes the selected provider and verifies its target contract.

User workflow

Compiler policy and feature policy are composed as Conan profiles

# 1. Locate the packaged compiler profile
base=$(uv run tula-cmake profile linux-gcc13-debug)

# 2. Compose compiler + feature policy
uv run conan install . \
  --output-folder=/tmp/build \
  --profile:all="$base" \
  --profile:all=profiles/logging-cpm \
  --build=missing

# 3. Configure and build with Conan's preset
cmake --preset conan-debug --fresh
cmake --build --preset conan-debug

Generation and resolution

The recipe generates a manifest; CMake resolves it explicitly

Read recipe optionsTulaConan._selection() converts Conan option values to FeatureMode.

Validate the selected feature graphUnsupported providers and disabled prerequisites fail before CMake.

Add Conan requirementsrequirements() adds packages only for features using the Conan provider.

Generate build inputsCMakeDeps, CMakeToolchain, presets, and tula_features.cmake.

Resolve after languages are enabledDownstream calls tula_resolve_features() after project().

Verify the logical targetEvery enabled feature must create tula::<feature>; disabled creates no target.

Expose resolved state to C++tula_add_config_header() generates version, availability, and provider macros.

Feature model

features.yaml is the provider registry; Python enforces its schema

logging:
  modes: [conan, cpm, system]
  dependencies: []
  conan_requires:
    - spdlog/1.15.3
  cmake_module: TulaLogging.cmake
  cmake_vars:
    FMT_URL: .../11.2.0.tar.gz
    FMT_SHA256: bc2306...
    SPDLOG_URL: .../v1.15.3.tar.gz
    SPDLOG_SHA256: 15a04e...

Validation performed by model.py

  • Registry is a non-empty mapping.
  • Modes are known, unique, and exclude implicit disabled.
  • Conan mode has at least one requirement.
  • Referenced CMake module exists.
  • Dependencies exist and form an acyclic graph.
  • Enabled features cannot depend on disabled features.
  • Manifest rendering is deterministic.
Sources: tula_cmake/features.yaml · tula_cmake/model.py

Logging provider

Four modes converge on one target contract

ModeAcquisition or discoveryUpstream targets expectedResult
disabledNo dependency work.None.No tula::logging target.
conanRecipe requires spdlog/1.15.3; Conan graph supplies fmt.spdlog::spdlog or header-only; fmt::fmt.tula::logging interface target links both and defines SPDLOG_ACTIVE_LEVEL.
cpmCPM 0.42.0 fetches checksummed fmt 11.2.0 and spdlog 1.15.3 archives.spdlog::spdlog; fmt::fmt.
systemfind_package(... CONFIG REQUIRED) for installed fmt and spdlog.spdlog::spdlog or header-only; fmt::fmt.

Important: Conan and system use the same CMake discovery function. Their difference is whether Conan populated the prefix path before configure.

Generated C++ contract

#define TULA_BOILERPLATE_VERSION "3.1.0"
#define TULA_BOILERPLATE_HAS_LOGGING 1
#define TULA_BOILERPLATE_LOGGING_PROVIDER "cpm"

The same source can compile with logging absent because target linking and C++ usage are both gated by resolved state.

The template currently exposes only the logging feature; it is not yet generic over future registry entries.

Wheel acceptance test

  1. Build the wheel from a copied package tree.
  2. Audit expected package data in the archive.
  3. Install into a fresh virtual environment.
  4. Locate the bundled GCC 13 profile through the CLI.
  5. Copy boilerplate outside the uv workspace.
  6. Run Conan/CMake with logging=system.
  7. Build and execute the downstream binary.

Not covered: a Conan package for Tula headers, install/export rules for tula::headers, or downstream consumption of Tula itself.

Technical gaps

The next work is contract completion, not provider expansion alone

Infrastructure gaps

  • Only one feature exists, so dependency ordering is not exercised.
  • The registry validates acyclicity but the resolver currently follows registry order, not an explicit topological order.
  • The generated config template is logging-specific.
  • Tula has no install/export/package rules.
  • The wheel gate covers only the system provider.

Software migration gaps

  • Active Tula headers are not compiled as part of the new gate.
  • Production Tula tests and examples have not been restored.
  • Behavior parity against refs/tula is not yet established.
  • kidscpp is not present in the active system.
  • Remaining production dependency features have not been designed or ported.
Sources: code review of active CMake/Python · design/TASKS.md
Recommended sequence

Prove generic behavior, then restore software coverage incrementally

Add one simple header-only featureUse registry-driven generic behavior; introduce a custom module only if the upstream contract requires it.

Add one real feature dependency edgeImplement explicit topological ordering and test disabled-prerequisite failure.

Make config-header generation data-drivenRemove logging-specific assumptions before the third feature is added.

Compile the Tula header surfaceAdd smoke translation units, then restore production tests by module.

Package Tula as a downstream dependencyAdd install/export and verify a separate consumer using the built package.

Integrate kidscpp lastRequire equivalent build/test behavior against the packaged Tula contract.

Milestone exit criterion: the new provider contract remains green while at least one real Tula module is compiled and tested through a packaged downstream workflow.
