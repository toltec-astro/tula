Resolution lifecycle

Provider choice is fixed before CMake runs

CMake does not choose

It receives a generated manifest and executes the already-validated mode after languages are enabled.

Profile selects a mode&:logging=disabled|conan|cpm|system

Python validates the graphMode support, prerequisites, and cycles are checked.

Conan adds only Conan requirementsCPM and system never enter the Conan dependency graph.

Generation emits one manifestCMakeDeps, toolchain, mode, variables, and module path.

Post-project resolution creates targetsEnabled features must produce tula::feature.

Config header records the resultC++ sees version, presence, and provider.

What the model enforces

  • disabled is implicit for every feature.
  • Conan mode must declare requirements.
  • Provider modules must exist in the wheel.
  • Dependencies must name known features.
  • The dependency graph must remain acyclic.
  • Immutable data is exposed through frozen structures.

Generated CMake

Resolution is visible, guarded, and target-based

project(tula_boilerplate ...)

include(TulaProject)
tula_resolve_features()
tula_add_config_header(
  TARGET tula_boilerplate_config
  ALIAS tula_boilerplate::config
  PREFIX TULA_BOILERPLATE
  OUTPUT tula_boilerplate/config.h
)

add_executable(tula_boilerplate src/main.cpp)
if(TARGET tula::logging)
  target_link_libraries(
    tula_boilerplate PRIVATE tula::logging
  )
endif()
  • Fails if called before project().
  • Fails if Conan’s manifest is absent.
  • Includes one provider module per enabled feature.
  • Fails if the provider does not create its normalized target.
  • Uses a global guard to resolve once.

Isolation rules

  • Every provider gets a fresh temporary Conan output folder.
  • Generated user presets are removed after the run.
  • CPM sources are cached, not build trees.
  • The wheel uses its own temporary Conan home.
  • Full logs remain under .devcontainer/logs/.
