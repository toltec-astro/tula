What the command does

The wrapper exposes three standard build phases

Bootstrap the Python tooluvx creates an isolated environment containing tula-cmake and Conan 2.31.1.

Install shared Conan configuration when requestedconan config install supplies organization remotes, profiles, settings, and hooks.

Resolve the package graphconan install --build=missing retrieves recipes, binaries, and python_requires.

Generate native build inputsCMakeDeps and CMakeToolchain write dependency configs, toolchain, and presets.

Select the generated presetThe CLI reads CMakeUserPresets.json; it does not reconstruct Conan's CMake arguments.

Configure and buildcmake --preset ... --fresh, then cmake --build --preset ....

Validation boundary

Pydantic models make the registry contract inspectable and fail-fast

class OptionSpec(BaseModel):
    model_config = ConfigDict(
        extra="forbid", frozen=True)

    values: tuple[str, ...]
    default: str
    cmake_variable: CMakeVariable

class FeatureSpec(BaseModel):
    name: Identifier
    modes: tuple[FeatureMode, ...]
    dependencies: tuple[Identifier, ...] = ()
    conan_requires: tuple[str, ...] = ()
    options: dict[Identifier, OptionSpec]

Validation performed before Conan generation

  • Unknown YAML keys are rejected.
  • Names and CMake symbols follow explicit patterns.
  • Option defaults must belong to their allowed values.
  • Conan-backed features must declare requirements.
  • Dependencies must exist and the graph must be acyclic.
  • Resolver wiring is derived from the validated feature name.
  • Models are frozen after validation.

The registry is configuration input, not an untyped dictionary passed between layers.

Python data flow

One registry instance feeds Conan options, requirements, and CMake state

load_registry()Parse YAML, inject keyed feature names, validate the model, and verify resolvers/<feature>.cmake exists.

TulaConan.init()Derive Conan option domains and defaults from FeatureSpec and OptionSpec.

TulaConan.requirements()Declare only the requirements belonging to features whose selected provider is Conan.

render_manifest()Emit provider modes, resolver paths, and immutable feature data in dependency order.

cmake_cache_variables()Project enabled-feature Conan options into the generated CMake preset.

TulaProject.cmakeDerive and call tula_resolve_<feature>_<mode>(), then verify its normalized target.

Single source of truth: Python never duplicates the logging or perflibs option tables outside registry.yaml.

Recipe implementation

The Conan mixin stays thin and delegates policy to validated models

class TulaConan:
    def init(self):
        self.settings = compose_settings(...)
        self.options.update(values, defaults)

    def requirements(self):
        for feature, mode in providers:
            if mode is CONAN:
                for ref in feature.requires:
                    self.requires(ref)

    def generate(self):
        render_manifest(...)
        toolchain.cache_variables.update(
            cmake_cache_variables(...))
        CMakeDeps(self).generate()
        CMakeToolchain(self).generate()

CLI implementation

Typer parses input; BuildWorkflow owns the state transition

class BuildRequest(BaseModel):
    source: Path
    output: Path
    profiles: tuple[str, ...] = ()
    options: tuple[OptionAssignment, ...] = ()
    config_source: str | None = None
    preset: str | None = None
    build_policy: str = "missing"

class BuildWorkflow:
    def execute(self):
        install_optional_config()
        ensure_profile_if_needed()
        conan_install()
        preset = read_generated_preset()
        cmake_configure(preset)
        cmake_build(preset)

Testability decisions

  • The command runner is injected as a typed callable.
  • Preset JSON crosses UserPresets and GeneratedPresets models.
  • The workflow consumes Conan’s preset instead of rebuilding its arguments.
  • Each --option NAME=VALUE becomes a root-scoped host option, &:NAME=VALUE.
  • CLI error translation is isolated from workflow logic.
  • Unit tests assert exact command order without spawning processes.

Current boundary

  • logging owns the compatible fmt + spdlog pair.
  • Consumers link only tula::logging.
  • yaml_cpp is one external package normalized as tula::yaml_cpp.
  • csv_parser declares only its evidenced CPM provider and exposes a pinned header tree.
  • netcdf_cxx4 depends on a separately selectable netcdf_c provider.
  • bitmask and meta_enum are separate pinned header-only package features.
  • clipp uses the same 1.2.3 source through Conan or CPM.
  • eigen depends on perflibs and normalizes Eigen3::Eigen.
  • Internal dependency splitting is deferred until the package matrix requires it.
  • perflibs is disabled or system-resolved; it does not pretend to be a downloadable package.
  • Every enabled resolver still creates one normalized tula::<feature> target.
  • Feature and provider derive both the module and tula_resolve_<feature>_<mode>() entrypoint.

Meta-feature implementation

All logging providers converge on the same fmt + spdlog target contract

function(tula_resolve_logging_conan)
  _tula_logging_installed()
  _tula_logging_finalize()
endfunction()

function(tula_resolve_logging_system)
  _tula_logging_installed()
  _tula_logging_finalize()
endfunction()

function(tula_resolve_logging_cpm)
  _tula_logging_cpm()
  _tula_logging_finalize()
endfunction()

Contract decisions

  • No independently selectable fmt feature or Conan option.
  • No resolver-level MODE switch; the driver dispatches by entrypoint name.
  • fmt and spdlog versions are selected together for the Conan provider.
  • CPM downloads both pinned archives with hashes.
  • System mode requires both config packages.
  • Compile-time log level becomes SPDLOG_ACTIVE_LEVEL.
  • Tula formatter headers are available whenever logging is enabled.

Conan 2.31 research

The implementation uses stable defaults and isolates experimental features

DecisionReason
Explicit conan install before CMakeConan documents install plus generated presets as the recommended general flow.
python_requires for shared recipe behaviorIt is the supported Conan distribution mechanism for reusable recipe code and exported helper files.
conan config install hook in bootstrapShared remotes, profiles, settings, hooks, and extensions stay organization-managed.
Keep stable CMakeDepsCMakeConfigDeps improves target fidelity but remains documented as experimental in 2.31.
Do not use cmake-conanIt moves installation into CMake and is documented as exceptional, with stability limitations.
Use isolated editable/local paths only for developmentReleased consumers resolve immutable package revisions from configured remotes.
