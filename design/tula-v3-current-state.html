What the command does

The wrapper exposes three standard build phases

Bootstrap the Python tooluvx creates an isolated environment containing tula-cmake and Conan 2.31.1.

Install shared Conan configuration when requestedconan config install supplies organization remotes, profiles, settings, and hooks.

Resolve the package graphconan install --build=missing retrieves recipes, binaries, and python_requires.

Generate native build inputsCMakeDeps and CMakeToolchain write dependency configs, toolchain, and presets.

Select the generated presetThe CLI reads CMakeUserPresets.json; it does not reconstruct Conan's CMake arguments.

Configure and buildcmake --preset ... --fresh, then cmake --build --preset ....

Conan graph

The downstream consumes a normal package, not superbuild internals

# tula_downstream/conanfile.py
class TulaDownstreamRecipe(ConanFile):
    name = "tula-downstream"
    version = "3.1.0"
    requires = "tula-boilerplate/3.1.0"
    generators = "CMakeDeps", "CMakeToolchain"
# downstream CMakeLists.txt
find_package(
  tula_boilerplate CONFIG REQUIRED)

add_executable(
  tula_downstream src/main.cpp)

target_link_libraries(
  tula_downstream PRIVATE
  tula_boilerplate::headers)

Boundary: tula_cmake is recipe/build infrastructure. It is resolved through Conan when recipe logic is needed; it is not a C++ link dependency propagated to consumers.

Feature model

The second feature now exercises dependency ordering and subsets

formatting:
  modes: [conan, cpm, system]
  dependencies: []
  conan_requires: [fmt/11.2.0]
  resolver: tula_resolve_package

logging:
  modes: [conan, cpm, system]
  dependencies: [formatting]
  conan_requires: [spdlog/1.15.3]
  resolver: tula_resolve_logging

Behavior now tested

  • Manifest order is formatting;logging.
  • Logging enabled with formatting disabled is rejected.
  • Both features can be disabled.
  • Formatting can be enabled while logging remains disabled.
  • Both features run through system, Conan, and CPM.
  • Every enabled resolver must create tula::<feature>.
Sources: features.yaml · model.py · profiles/formatting-only
CMake implementation

Generic packages and semantic exceptions use different resolvers

ResolverFeatureResponsibilities
TulaPackage.cmakeformattingUse registry package/target metadata; run config-mode discovery or checksummed CPM; choose a declared upstream target; create tula::formatting.
TulaLogging.cmakeloggingRequire tula::formatting; resolve spdlog; validate log level; add SPDLOG_ACTIVE_LEVEL; create tula::logging.
TulaCPM.cmakeshared helperLoad pinned CPM 0.42.0 once, verify its hash, and honor the external source cache.
TulaProject.cmakeall featuresExecute manifest order, call the declared resolver, verify logical targets, and record selected providers.

Data-driven C++ state

The configuration header now follows the registry automatically

# generated for a formatting-only build
#define TULA_BOILERPLATE_VERSION "3.1.0"

#define TULA_BOILERPLATE_HAS_FORMATTING 1
#define TULA_BOILERPLATE_FORMATTING_PROVIDER "system"

#define TULA_BOILERPLATE_HAS_LOGGING 0
#define TULA_BOILERPLATE_LOGGING_PROVIDER "disabled"

Generation logic

  • TulaProject.cmake stores the resolved feature list globally.
  • tula_add_config_header() iterates that list.
  • Feature names are normalized to uppercase macro suffixes.
  • Availability is derived from the normalized CMake target.
  • Provider values come from resolver state.

Adding a registry feature no longer requires editing the header template.

Sources: TulaConfigHeader.cmake · TulaConfig.h.in

Conan 2.31 research

The implementation uses stable defaults and isolates experimental features

DecisionReason
Explicit conan install before CMakeConan documents install plus generated presets as the recommended general flow.
python_requires for shared recipe behaviorIt is the supported Conan distribution mechanism for reusable recipe code and exported helper files.
conan config install hook in bootstrapShared remotes, profiles, settings, hooks, and extensions stay organization-managed.
Keep stable CMakeDepsCMakeConfigDeps improves target fidelity but remains documented as experimental in 2.31.
Do not use cmake-conanIt moves installation into CMake and is documented as exceptional, with stability limitations.
Use isolated editable/local paths only for developmentReleased consumers resolve immutable package revisions from configured remotes.
Source: official Conan 2.31 documentation
