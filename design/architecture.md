# Tula architecture

How the repository realizes the specification (`design/spec.md`).

## Repository layout

```text
tula/
├── CMakeLists.txt               options, module requirements, targets, install
├── cmake/tulaConfig.cmake.in    installed package configuration
├── include/tula/                headers of all components; config.h.in
├── spack_repo/
│   ├── develop.yaml             tula → repository root
│   └── toltec/tula/packages/    tula and the Tula-only adapters
├── tests/                       behavior tests and installed-consumer projects
└── examples/
```

## Component wiring

The same component edges are stated twice, at two stages:

| Stage | Where | Effect |
| --- | --- | --- |
| Concretization | recipe `requires("+<child>", when="+<parent>")` | Spack rejects an inconsistent variant set before any build |
| Configuration | `tula_require_module(<PARENT> <CHILD>)` in `CMakeLists.txt` | a plain CMake build with inconsistent options fails |

The recipe maps each variant to `TULA_ENABLE_<COMPONENT>` with
`define_from_variant`, and adds `depends_on` edges only `when` the variant is
on, so a disabled component brings no dependency into the graph.

`tula_add_module(<name> <requirements>...)` creates the interface library
`tula_<name>`, exports it as `tula::<name>`, and links `tula::core` plus the
requirements. All components are header-only interface targets.

## Installed package

`tulaConfig.cmake` is configured with the enabled options:

1. it calls `find_dependency` for the adapter packages (and Ceres) of the
   enabled components only;
2. includes `tulaTargets.cmake`;
3. sets `tula_<component>_FOUND` for each exported `tula::<component>`
   target;
4. calls `check_required_components(tula)`, so a missing requested component
   sets `tula_FOUND` to false.

## Generated headers

- `<tula/config.h>` is generated by `tula_cmake_generate_config_header()`
  from `TULA_HAS_<COMPONENT>`, which the build sets from
  `TULA_ENABLE_<COMPONENT>`.
- `<tula/version.h>` is generated by `tula_cmake_generate_version_header()`;
  the recipe passes `TULA_PACKAGE_SPEC` and `TULA_DAG_HASH`.
- `<tula_perflibs/config.h>` belongs to the `tula-perflibs` adapter and
  reports `TULA_PERFLIBS_HAS_THREADS` and `TULA_PERFLIBS_HAS_OPENMP`. Tula's
  `TULA_HAS_PERFLIBS` and `TULA_HAS_OPENMP` do not define or read them.

## Tests

`tests/CMakeLists.txt` adds a behavior test for each enabled component
(`tula_add_behavior_test`), so a build runs the tests of its own closure. The
recipe's `check` fails when a build configures no test. The
`*_consumer/` and `missing_component/` projects are configured against the
installed package by the TulaCMake gates.

With `ecsv`, the build also compiles `examples/ecsv_reader` and adds
`tula::ecsv_reader_real_tunes`, which reads real tune reports under
`TOLTECA_TEST_DATA_ROOT`: the work-directory reports
(`tolteca_workdir/data/*_tune.txt`) when their links resolve, else
`data_lmt/toltec/reduced/*_tune.txt`. Without reports the test is not added.
